## 二、回首页不再重新请求：模块级缓存

问题是经典 SPA 通病：`App.tsx` 用标准 `<Routes>`，`/` ↔ `/post/:slug` 来回切，`Home` 卸载再挂载，`useEffect([])` 每次都重新拉全量文章列表——从详情页返回首页必然又转一圈圈。

修法是在 `Home.tsx` 加一个**模块级缓存**（注意不是 `localStorage`，模块级就够，刷新页面自然清掉）：

```ts
type PostsCache = { data: Post[]; ts: number }
let postsCache: PostsCache | null = null
const POSTS_CACHE_TTL = 60 * 1000
```

`useState` 初始值直接读缓存，`loading` 初始为 `!postsCache`——**有缓存时秒显列表、不闪"加载中"**；命中且未过期直接返回不发请求；首次/过期才真正请求，过期但有旧数据时走**后台静默刷新**（不闪加载态），兼顾新鲜度。

缓存带来一个副作用：作者刚发完文 60 秒内回首页可能看不到新文。闭环办法是 `Home.tsx` 导出 `invalidateHomeCache()`，`Admin.tsx` 在发布/改状态/删除三处成功后调用——作者侧立即重拉，游客侧继续白嫖缓存。书签页也是同一套模式，只是 cache key 不同。

## 三、原生弹窗大清扫：Toast + 自定义确认框

`alert` 有多难用不用解释：锁屏、样式丑、关不掉复制不了错误信息。这次做了套全局 Toast：

- `src/lib/toast.ts`：模块级事件总线，`toast(message, type)` 任意位置可调；
- 宿主组件基于 `useSyncExternalStore` 订阅，挂在 `App.tsx` 顶层；
- 顶部居中、3.2s 自动消失、**不阻断操作**，带 ✓/! 图标按类型配色（success 绿 / error 红 / info 灰）；
- **同内容自动合并**——正文图片连续上传时压缩提示不会刷屏。

`Admin.tsx` 里 7 处原生弹窗全部替换：封面压缩提示 → 绿色 Toast；标题/路径/正文校验失败 → 红色 Toast；上传/保存失败 → 红色 Toast（文案可选中复制）；删除确认 `window.confirm` → 复用项目既有 `.confirm-modal` 样式的自定义模态（createPortal 挂 body，点遮罩可取消）。顺带补了删除成功的 Toast——原来成功失败都没提示，现在反馈齐全。

## 五、书签功能：名称/网址/分类/创建时间/介绍

个人博客常有一个痛点：常用网站散落在浏览器收藏夹，换台电脑就抓瞎。这次把它做成站点功能。

**数据库**（`supabase/bookmarks.sql`，字段完全按需求）：

| 字段 | 类型 | 说明 |
|---|---|---|
| `name` | text | 名称 |
| `url` | text | 网址（没写协议自动补 `https://`） |
| `category` | text | 分类（自由输入 + datalist 建议） |
| `created_at` | timestamptz | 创建时间（默认 now()） |
| `description` | text | 介绍 |

RLS 公开读、登录可管理，授权方式与 `posts` 一致。

**前台 `/bookmarks`**：按分类分组的卡片网格，顶部本地搜索（名称/介绍/网址/分类四合一过滤），点击新标签页打开，60s 模块级缓存 + 后台改完主动失效。

**后台 `/admin`**：新增一级页签"文章管理 / 书签配置"，表格列出全部书签支持增改删，删除走自定义确认模态（没退回原生 confirm，前面的改造没白做）。

写完顺手用登录态 REST 种了 26 个常用网站（开发 11 / 工具 5 / 学习 4 / 设计 4 / 社交 2），基本覆盖前端日常。

## 七、踩坑：Supabase 重跑 SQL 报 42710

新游戏加进排行榜要扩展 `game_scores` 表的 CHECK 约束，让用户重跑 `game_scores.sql`，结果报：

```
ERROR: 42710: policy "anyone can read game scores" for table "game_scores" already exists
```

原因很朴素：文件里 `create policy` 前面没写 `drop policy if exists`，第一次执行时 policy 已创建，再跑就撞"已存在"。项目里 `schema.sql` / `bookmarks.sql` 本来就带前置 drop，漏改的是另外三个文件（`game_scores` / `post_likes` / `visitor_locations`）。

```sql
-- 修法：每条 create policy 前补前置 drop
drop policy if exists "anyone can read game scores" on game_scores;
create policy "anyone can read game scores"
  on game_scores for select using (true);
```

教训：**凡是可能被重复执行的 SQL 文件，每条语句都要写成幂等**——`create table/index if not exists`、`create or replace function`、`drop policy if exists` + `create policy`，一个都不能漏。更阴的是：这次报错发生在 policy 创建步，**文件末尾的 DO 块（扩展 CHECK 约束）被中断没执行**，等于用户以为跑完了其实没有——下次报错信息要提醒自己确认失败点之后的内容是否也没跑。

## 八、移动端：只留中间内容

最后一刀切给手机：新增 `@media (max-width: 720px) { .page-shell .sidebar { display: none } }`——左栏（头像卡片 + 打赏二维码）和右栏（时间/访客/运势/游戏中心）在手机上整体隐藏，白卡撑满可用宽度。

- 断点选 720px：项目既有的移动断点（头部导航、分页都在这个值），保持一致；
- 纯 CSS 零 JS 改动，组件挂载逻辑没动，桌面端零回归风险；
- 容器宽度复位不用重写，既有 1180px 块的 `.container.has-sidebars` 规则在 720px 下依然生效，不会横向溢出。

## 九、小结

一天下来其实就一条主线：**把博客从"能写能看"往"好用"推进**。沉淀几条：

1. **SPA 列表页用模块级缓存**（60s TTL + 后台静默刷新 + 发布后主动失效），游客秒开、作者立即可见，两头都顾；
2. **原生 `alert`/`confirm` 是体验洼地**，一套 Toast 事件总线 + 自定义确认模态全站复用，同内容合并防刷屏；
3. **工具类功能拆独立路由**，页面职责单一，导航入口清晰；
4. **SQL 文件必须全幂等**，`drop if exists` 前置一个都不能少，否则重跑即翻车；
5. **移动端适配优先"做减法"**：小屏直接隐藏非核心侧栏，比强行堆叠更干净。
