> 同样是把界面放大缩小，`transform: scale` 和 `zoom` 一个是「拍照缩放」，一个是「重新排版」。选错了刀，文字模糊、图表发虚、弹窗错位就会轮番找上门。这篇用我们能源运维大屏的真实踩坑经历，把两者的差异一次讲透。

## 一、背景：一套代码，三种屏幕

我们的富能智慧运维大屏要在三种环境里跑：

- **1920×1080**：常规浏览器 / 投屏，标准 16:9；
- **3200×1080**：超宽拼屏（5×3 拼接的一部分），宽高比接近 3:1；
- **872×522**：嵌入式小屏终端，低分辨率、性能弱。

设计稿只有一套 1920×1080。适配的核心问题就一个：**用什么方式把 1920 的内容塞进别的分辨率，还能保持清晰、可交互**。

在这个过程中，`transform: scale` 和 `zoom` 我们都用到了，也把两者的脾气摸了个遍。

## 二、transform: scale：视觉层的「照相机」

```css
.screen {
  width: 1920px;
  height: 1080px;
  position: absolute;
  left: 50%;
  top: 50%;
  margin-left: -960px;
  margin-top: -540px;
  transform: scale(scaleX, scaleY); /* 宽高独立缩放 */
  transform-origin: top left;
}
```

`scale` 是 CSS Transform 的一部分，本质是**图形变换**：元素先按 1920×1080 完成布局和渲染，浏览器再把渲染结果当作一张「图」进行缩放。这带来几个关键特性。

**1. 不影响布局。** transform 不改变元素在文档流中占据的空间。缩放后元素视觉上变大了，但它占的布局空间还是 1920×1080。所以大屏适配的经典写法是配合 `position: absolute + 50% + 负 margin` 居中，让「布局尺寸」和「视觉尺寸」脱钩。

**2. 可以独立拉伸 X/Y。** `scale(1.67, 1)` 可以只拉宽不拉高——这正是 3200×1080 超宽屏的适配思路之一（我们最终没这么用，因为拉伸会变形，后面说）。

**3. 缩放是「事后」的。** 文字、canvas、图片都按原始尺寸渲染，再整体被放大或缩小。**放大时文字发虚**（按位图插值放大），缩小时还可以接受。echarts 这类 canvas 图表在 scale 放大时模糊得尤其明显，因为 canvas 的物理像素是按 CSS 尺寸 × dpr 画的，不感知 transform。

**4. 事件坐标不用换算。** `e.clientX/clientY` 是视口坐标，`getBoundingClientRect()` 返回的也是变换后的视觉矩形，两者天然对齐。但如果你手写过 `offsetLeft + clientX` 之类的混合计算就会踩坑——`offsetLeft` 是布局坐标，不感知 transform。

**5. 一个隐蔽的坑：fixed 失效。** 父级元素一旦有 transform，子元素的 `position: fixed` 会退化为相对该父级定位。Modal、Loading 遮罩这类依赖 fixed 的组件，在 scale 容器里经常「飘」到错误的位置，就是这个原因。

## 三、zoom：布局层的「重新排版」

```css
.screen {
  zoom: 0.483; /* 整个布局按比例重新计算 */
}
```

`zoom` 走的是完全另一条路：它**参与布局计算**。设置 `zoom: 0.5` 后，元素内部所有内容按 50% 的比例重新排版——文字真的用 12px×0.5 的大小排布，canvas 真的以更小的物理尺寸重画。

**1. 清晰度是它最大的优势。** 因为是真实重排，缩小后的文字依然锐利，echarts 图表物理分辨率匹配实际显示尺寸，不发虚；放大时同样清晰。

**2. 兼容性已经不是问题了。** `zoom` 曾经是 IE/Chrome 的私有属性，Firefox 长期不支持——这是它被 scale 压制多年的原因。但 2024 年 zoom 被纳入标准（Interop 2024），Firefox 126 起正式支持，Safari 更早就支持。现在三大浏览器都能用。

**3. 它参与布局，所以「占地方」。** zoom 后元素占据的布局空间就是缩放后的尺寸，父容器的 flex/grid 会按缩放后的尺寸排列它。这既是特点也是约束——不能再靠「布局尺寸不变」的老套路居中。

**4. 只有一个维度。** `zoom` 只接受单一比例，不能像 `scale(1.67, 1)` 那样宽高独立拉伸。

**5. 最阴险的坑：长度被 zoom 乘。** zoom 元素内部的 `margin`、`left`、`top` 等长度值，视觉位移会被 zoom 再乘一次。经典的「absolute + left:50% + margin-left:负一半」居中公式在 zoom 容器里直接翻车——负 margin 也被 zoom 缩小了，中心对不上。我们的解法是：**zoom 元素统一 `left: 0; top: 0` 起步，居中交给外层 flex**。

## 四、差异速查表

| 维度 | transform: scale | zoom |
| --- | --- | --- |
| 本质 | 图形变换（渲染后缩放） | 布局参与（重新排版） |
| 文字/图表清晰度 | 放大模糊，缩小尚可 | 缩放都清晰 |
| 布局占位 | 不变（占原尺寸） | 变为缩放后尺寸 |
| X/Y 独立拉伸 | 支持 `scale(x, y)` | 不支持，单一比例 |
| margin/left 等长度 | 不受影响（布局坐标） | 视觉上被 zoom 乘 |
| `position: fixed` 子元素 | 退化为相对 transform 父级定位 | 正常 |
| 性能 | 不触发重排，但大区域重绘 | 触发重排，内容多时开销更大 |
| 兼容性 | 全平台 | Chrome/Safari 一直支持，Firefox 126+（已标准化） |
| `getBoundingClientRect` | 返回变换后视觉尺寸 | 返回缩放后视觉尺寸（`offsetWidth` 等布局属性仍是未缩放 CSS 值） |

## 五、实战：三种屏幕是怎么选的

### 1920×1080：scale(1, 1)，等于没用

基准分辨率，`scale(1,1)` 完全无变化。这套 transform 方案的真正价值在别的分辨率上。

### 3200×1080 超宽屏：都不用，原生渲染

宽高比 3:1，无论 scale 还是 zoom 都会面临「等比缩放留黑边 vs 独立拉伸变形」的两难。我们的选择是**第三条路：完全不缩放**——容器原生 100%×100%，页面内部全部用 flex/百分比弹性布局。高度 1080 原样、字体 1:1，多出来的宽度自动摊给三栏面板。**适配的最高境界是不适配**：布局本身弹性化，比任何缩放都干净。

### 872×522 小屏：zoom 为主、scale 补刀

872/1920 = 0.454（宽系数），522/1080 = 0.483（高系数）。两个系数不一样，纯 zoom 只能取一个，铺不满或超出；纯 scale 又会模糊。最终组合拳：

```ts
const fx = winW / 1920;        // 0.454
const fy = winH / 1080;        // 0.483
const z = Math.max(fx, fy);    // 0.483，zoom 占满较大轴

// zoom 负责高清重排，scale 只补齐 zoom 没铺满的那一轴（压缩方向 ≤1，不产生模糊）
`transform: scale(${fx / z}, ${fy / z}); zoom: ${z};`
```

- `zoom: 0.483`：文字和 echarts 按 0.483 倍真实重排，小屏上依然清晰；
- `transform: scale(0.94, 1)`：zoom 只铺满了高度轴，宽度还差一点，scale 在**压缩方向**（≤1）补齐——压缩不会放大像素，所以不牺牲清晰度。

两个叠加时还有个细节：zoom 元素内的 transform 长度也会被 zoom 影响，所以 `transform-origin` 必须是 `top left`、定位从 `left: 0; top: 0` 起步，让两种变换共享同一个原点，数学上才不会互相打架。

这套判定集中在一个 `innerRootCss(scaleX, scaleY)` 函数里，配上视口监听实时切换：视口 `宽 ≤1024 且高 ≤640` 走小屏模式，1920 与 3200 仍走各自原有分支，代码路径互不干扰，一个构建就能覆盖三种屏幕。

## 六、选型建议

一句话总结：

- **要等比缩放、追求文字图表清晰** → 优先 `zoom`（Firefox 126+ 已无兼容顾虑）；
- **要宽高独立拉伸铺满、或需要保持布局占位** → `transform: scale`；
- **低分辨率小屏** → `zoom` 打底 + `scale` 反向补差，清晰度和铺满兼得；
- **超宽/异形屏** → 别缩放了，把布局做成弹性的，一劳永逸。

另外无论选哪个，都建议把「分辨率 → 模式」的判定集中在一个函数里，别散落在各个组件。缩放是最后一道防线，弹性布局才是第一道。
