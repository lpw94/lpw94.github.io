## 🐛 SQL 首次执行失败：42501（已修）
- 用户跑 `post_pdfs.sql` 报错：
  `42501: Direct deletion from storage tables is not allowed. Use the Storage API instead.`
  `CONTEXT: PL/pgSQL function storage.protect_delete() line 5 at RAISE`
- 根因：脚本末尾为了清临时探测 PDF 写了
  `delete from storage.objects where bucket_id='covers' and name like 'pdfs/__probe-%'`；
  Supabase 在 `storage.objects` 上挂了 `protect_delete()` 触发器，**禁止任何直接 DML 删除**。
- 🔴 **更关键的连带效应**：SQL Editor 把整份脚本当**一个事务**，最后一句报错导致
  **前面的 `alter table add column` 和 `create policy` 一起回滚**。
  事后 REST 探测确认 `pdf_url` / `pdf_name` 仍都是 42703，所以不是「只需清理文件」，
  而是必须**重跑整份修好的脚本**。
- 修法：删掉 `delete` 语句，改成注释说明只能走 Storage API / Dashboard 清理；
  并在文件头补「整份脚本单事务；policy 段若报权限错可只跑两行 alter table」的提示。
  脚本现在只剩 DDL（2 × alter table + drop/create policy）。
- 探测脚本 `scripts/publish/expr-probe-pdf-sql.js`（本地 gitignore）验证结论：
  两列都不存在；`storage/v1/object/list/covers?prefix=pdfs/` 返回两个遗留文件
  `__probe-1794447827357.pdf` / `__probe-1794447894059.pdf`（各约 500B）。
  本机 `extract-access.mjs` 已扫不到未过期 access_token（3 个都过期），
  所以暂时无法用 Storage API 自动清理；等用户重新登录 `/admin` 后再清，或手动删。
- 修复已提交到 dev，**未推 main**（用户没要求）；main 上的 `post_pdfs.sql` 仍是旧版，
  用户当前应使用本地已修好的这份。
